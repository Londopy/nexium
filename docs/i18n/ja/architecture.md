# Nexium の仕組み

コンパイラを理解したい人、変更したい人のためのガイドツアーです。言語リファレンスは [`language.md`](language.md)、他の言語から Nexium を呼ぶ方法は [`embedding.md`](../../embedding.md)（英語）、仕様が決めていなかった箇所で下したすべての判断は [`DECISIONS.md`](../../../DECISIONS.md)（英語）にあります。

## 自分自身で書かれた一つのコンパイラ

コンパイラは `self/` の下に Nexium で書かれています。`lexer.nx`、`parser.nx`、検査器（`check.nx` とその隣の `check_*.nx` モジュール、そして `cimport.nx`）、`cgen.nx`、ドライバの `nx.nx` がそれぞれ下で説明する各段階にあたり、その後にツール（`fmt.nx`、`doc.nx`、`tools.nx`、`size.nx`、`manifest.nx`、`ship.nx`、`ship_node.nx`、`installer.nx`、`lsp.nx` と `lsp_index.nx`、`repl.nx`、`topo.nx`、`completions.nx`、`fix.nx`）が続きます。コンパイラは `bootstrap/` にある C のシードから自分自身をビルドします（決定 90）。最初のコンパイラは Rust で書かれ、移植を牽引し、1.0 で退きました。

## 一段落で言うと

`nx` は `.nx` ソースを読み、検査し、一つの C ファイルを書き出します。その C ファイルは `runtime/nx_rt.h`（コンパイラのバイナリに埋め込まれた約 4,200 行の素朴な C）をインクルードし、クロスコンパイル用の libc を同梱した Clang である `zig cc` に渡されます。ガベージコレクタも仮想マシンも、インストールすべきランタイムライブラリもありません。出力はネイティブの実行ファイル、共有ライブラリ、または静的アーカイブで、ターゲットの C ライブラリにしか依存しません。

```
 hello.nx ──lex──▶ tokens ──parse──▶ AST ──check──▶ 型付き IR ──cgen──▶ hello.c ──zig cc──▶ hello.exe
                                            │
                                            └──comptime──▶ 定数値、comptime テスト
```

## パイプライン、段階ごとに

### 1. 字句解析器（`self/lexer.nx`）

バイトを受け取り、トークンを返します。ここでの二つの決定が、下流のすべてを形作ります。

- **改行はトークンです。** 文は改行で終わるので、字句解析器は `Newline` を出し、連続する改行を一つにまとめます。`(` と `[` の内側では改行が抑制され、これが引数リストを複数行にまたがって書ける理由です。`{ }` の内側では改行は保持されます。ブロック内の文は改行で区切られるからです。
- **`<<` と `>>` は `LtLt` と `GtGt` であり、決してシフト演算子ではありません。** バイナリパターンを開くのかビットをシフトするのかは、構文解析器が文脈から判断します。

識別子、キーワード、組み込みの名前はすべて `Ident` です。キーワードは構文解析器が認識します（`KEYWORDS` がその一覧です）。文字列とコメントの外にある非 ASCII 文字はエラーです。求められれば、字句解析器は `//` コメントをトークンとして残します。フォーマッタはそれを必要とし、構文解析器は決してそれを見ません。

### 2. 構文解析器（`self/parser.nx`）

再帰下降で、文法規則ごとに一つの関数があり、`Tree` を作ります。`Tree` は `Node`（種類、子、名前、テキスト、三つのスロット `x`、`y`、`z`）の id アリーナで、その上にモジュールの項目（関数、struct、enum、trait、impl、定数、グローバル、import、テスト、アーティファクト）が載ります。ドキュメントコメントは `Tree.docs` へのインデックスで保持されます。条件は括弧なし（`if c {`。そこで構造体リテラルを書くには括弧が必要）、構造体リテラルは `Point{ .x = 1 }`、無名のものは `.{ .x = 1 }`、クロージャのキャプチャは `|[x, &mut y] a: i32|` のように明示的に書きます。

行継続の規則は構文解析器にあります。`|>`、`.method(`、`catch`、`orelse`、`and`、`or` で始まる行は前の行に続き、二項演算子や閉じていない括弧で終わる行も同様です。

### 3. 検査器（`self/check.nx` と `self/check_*.nx`）

コンパイラで最も大きな部分で、約 16,000 行です。構文木を型付き IR（`Tir`。これも id アリーナで、ノードごとに `TKind` を持つ）に変換し、すべての診断を生成します。その状態は `check.nx` にある一つの struct `Checker` で、同じファイルに中核があります：型、定義、読み込み、インスタンスとプログラム全体に対するパス、ジェネリックな環境、所有権、単一化、範囲です。残りのメソッドはそれぞれ独自のモジュールにあり、各モジュールは一つの `impl Checker` ブロックです（決定 110）。`check.nx` がそれらすべてをインポートすることで、それらはプログラムの一部になります：

| モジュール | 検査するもの |
| --- | --- |
| `check_stmts.nx` | 本体、ブロック、文、ループ |
| `check_views.nx` | ビューとその由来、規則 V1〜V5 |
| `check_exprs.nx` | 式、関数呼び出し、`if`、キャスト |
| `check_fields.nx` | フィールド、リテラル、添字、`try`、`catch`、`orelse` |
| `check_calls.nx` | メソッド、静的メンバー、組み込み名前空間 |
| `check_match.nx` | `match`、パターン、網羅性 |
| `check_builtins.nx` | `@` 組み込み、レイアウト |
| `check_closures.nx` | クロージャ |
| `check_print.nx` | `nx tir` 用の、テキストとしての型付き IR |
| `check_interp.nx` | コンパイル時インタプリタ（第 4 節） |

構成要素は次のとおりです。

**型はインターンされます**（`Types`）。型は `Ty` のテーブルへのインデックスで、二つの型が等しいのはインデックスが等しいときだけです。推論変数もテーブルの項目なので、`let x = 0` は `x` に整数変数を与え、それを確定させる最初の使用で解決されるか、既定で `i64` になります。

**ジェネリクスは単相化されます。** `fn max(comptime T: type, a: T, b: T)` は、呼び出された異なる `T` ごとに一度検査され、組み合わせごとに一つの `Inst` ができます（`instantiate`）。型パラメータに実行時の表現はありません。トレイト制約（`where T: Ord`）はインスタンス化のときに検査され、`impl` ブロックは構造的に照合されます。

**所有権は関数ごとのフロー解析です。** `List`、`String`、`Map` の値は所有されます。値で代入したり渡したりするとムーブされ、検査器は元のローカルをムーブ済みとしてマークします（`FnCtx.moved`。分岐ごとにスナップショットを取り、合流させます）。再び使うと `use after move` エラーです。フィールド、要素、ループ変数、場所に対する `if let` 束縛からのムーブは、コンテナが半分だけ所有された状態になるため拒否されます。引数は借用なので、呼ばれた側はそれをムーブできません。`ref class` の値は参照カウント付きのポインタで自由にコピーでき、検査器はそれが `refcounts` を必要とすることだけを記録します。

**エフェクトは不動点で推論されます**（`propagate_effects`）。本体を検査する間、検査器は関数が直接行うエフェクト `own_effects` を、それぞれ*証人*（位置と、それを説明する一文。例："appending to a List may grow it"）付きで記録します。すべての呼び出し先も記録します。その後

```
effects(f) = own(f) ∪ ⋃ effects(callee)      不動点まで反復
```

をすべてのインスタンスに対して計算します。extern 関数は何でもすると仮定されます。シグネチャや関数型の `!allocates` のような負の制約は伝播の後に検査され、診断は呼び出しグラフをたどってエフェクトを持ち込んだ関数まで行き、その証人を表示するので、エラーは呼び出し連鎖の一番下にある正確な行を名指しします。`panics` は、操作が失敗し得ないと検査器が証明できる場所で免除されます：同じスライス上の `for` のループインデックスによる添字、コンパイル時に既知の添字、オペランドの範囲が収まる算術です。

束は 8 ビットです（`EFF_*`）：`allocates`、`refcounts`、`blocks`、`shared_mutable`、`nondeterministic`、`panics`、`ffi`、そして呼び出しグラフから決まる `unbounded_stack`。循環上にある関数（`mark_recursion` での Tarjan の強連結成分）や、関数値や `dyn` を通して呼び出す関数がこれを持ちます。

**パターン**（`check_match`）は `match` を決定木にコンパイルし、enum と bool について網羅性を検査します。**バイナリパターン**は `<<len:16/little, payload:len*8, rest:bytes>>` を、サイズが前の束縛に依存し得る検査付きビット読み取りの列に変えます。

**ビュー**はその由来で追跡されます（`self/check_views.nx`）。各ローカルは、自分が持つビューがどの記憶域を指しているか、それがいつ取られたかを知っており、`SPEC.md` 5.6 と 5.7 の規則 V1〜V5 は、解放済みの記憶域を読むことになる使用箇所で検査されます。1.3 からエラーです（1.2 では警告）。修正が機械的な場合、検査器は `nx fix` に編集案を渡し（`check.Fix`：ムーブ箇所での V4 の `.clone()`、V5 の `@escape`、未使用の値の前の `_ = `）、`self/fix.nx` は、編集後のプログラムを検査してエラーが減り、新しいエラーが出ない場合にだけそれを採用します。関数のローカルへのスライスやポインタを返すこと（規則 R1）は 1.0 からエラーです。

**トレイトオブジェクト**は (trait, 型) の組ごとに vtable を得ます。vtable はレシーバを合わせるサンクとして生成されます。`dyn Shape !allocates` は別の型で、そこへ変換されるすべての実装がその制約を満たさなければなりません。

**`@cImport`**（`self/cimport.nx`）はヘッダに `zig cc -E` を実行し、出てきた宣言を小さな C 宣言パーサで読み、合成モジュールを注入します。生成される C はヘッダ自身の型名を使うので、レイアウトについてはヘッダが唯一の情報源であり続けます。

### 4. コンパイル時評価（`self/check_interp.nx`）

型付き IR 上のインタプリタで、値は `CV` で表されます。その `it_*` 関数は独自のモジュールで宣言された検査器のメソッドなので（決定 110）、検査器はそれらを自分のメソッドとして呼び、それらは検査器のテーブルを直接読みます。`comptime expr`、`const` の初期化子、`@embedFile`、`comptime test` ブロックは検査中にここで実行されます。純粋な計算、コレクション、Nexium 関数の呼び出しは許され、I/O、時計、乱数、外部呼び出し、グローバルは禁止されます。ステップ予算があるので、暴走した評価はハングではなくコンパイルエラーになります。失敗した `comptime test` は、他のエラーと同じく `expect` の行で報告されます。同じインタプリタが `nx repl`（`self/repl.nx`）を実行し、そこでは `repl_mode` によって外の世界とやり取りでき、プレイグラウンドの実行器である `nx play` も実行し、そこでは `play_mode` がページにできないことを拒否します。

### 5. C バックエンド（`self/cgen.nx`）

型付き IR は一つの C 翻訳単位に落とされます。`nx emit-c` の出力に見えるものの大半は、いくつかの約束事で説明できます。

- **すべての関数は隠れた `nx_ctx* c` を受け取ります。** コンテキストはアロケータ、現在のアリーナ、stdout/stderr、乱数生成器の状態、argv、リーク追跡のカウンタを運びます。ランタイムにグローバルはなく、それが出荷されたライブラリをホストプロセスに安全に読み込める理由です。
- **所有された値はスコープ終了時にドロップされます。** バックエンドはスコープのスタックを持ち、所有型の各 `Let` がドロップを登録し、スコープを抜けるとき（通常の終了、`return`、`break`、エラーのいずれでも）、`defer` とともに逆順でドロップを出力します。呼び出しに渡された一時値も登録されます。
- **検査付き算術は関数呼び出しです。** `x * 7` は `nx_mul_i64(x, 7, "hello.nx:3")` になり、位置の文字列はパニックのときに表示されるものです。回り込み（`*%`）と飽和（`*|`）の形は、素の C か、値を範囲内に収めるヘルパに対応します。
- **パニックは `longjmp` です。** スレッドローカルの `nx_boundary` が `jmp_buf` を持ち、`nx_panic` はメッセージと位置を埋めて、エントリポイントかエクスポートのラッパーが設置した最寄りの境界へジャンプします。
- **`for parallel`**（`parallel_for`）は本体をワーカー関数に取り出し、外側のローカルにはポインタの構造体を通して到達させ、ランタイムがインデックス範囲をハードウェアスレッドに分割します。ワーカーのパニックは捕捉され、全ワーカーの終了後に呼び出し側で再送出されます。
- **`using arena`** は、ブロックの間、コンテキストのコピーにバンプアロケータを差し込みます。コンテナは自分が作られたアリーナを覚えているので、ブロック内で伸びる外側の `List` はヒープに住み続けます。

これは降下（lowering）後の `examples/hello.nx` です：

```c
static void nx_main(nx_ctx* c) {
  nx_sink _t1 = nx_sink_file(c, c->out);
  nx_w(&_t1, (const uint8_t*)nx_str_0, 13);
  nx_w(&_t1, (const uint8_t*)"\n", 1);
  nx_sink_flush(&_t1);
  int64_t x_0 = nx_mul_i64(((int64_t)6LL), ((int64_t)7LL), "examples/hello.nx:3");
  ...
}
```

書式化は解釈ではなくコンパイルされます。`println("x = {}", .{x})` は、引数の型がわかった上で、プレースホルダごとにシンクへ直接書き込む処理になります。

### 6. ランタイム（`runtime/nx_rt.h`）

一つのヘッダで、`@embedFile` でコンパイラに埋め込まれ、生成される各ファイルの先頭に貼り付けられます。節は、スライス、アロケータのインターフェース、パニック、任意のリーク追跡付きの既定（malloc）アロケータ、アリーナ、parallel-for のスレッドプール、リスト、文字列、書式化、ハッシュマップ、参照カウント、バイナリパターンのヘルパ、検査付き算術、そして Windows と POSIX 向けのプラットフォーム部分です：ファイルシステムとファイルハンドル、時間、プログラムの起動と子プロセス、ソケット、システム自身のライブラリによる TLS、スレッド、端末の生の入力。

参照カウントは、各 `ref class` オブジェクトの前に置かれた 2 ワードのヘッダ（`rc`、`weak`）です。`nx_retain` はランタイムにあるインライン化されたインクリメントで、解放はバックエンドがクラスごとに生成します（`cgen.nx` の `drop_fn`）。カウントがゼロになったとき、オブジェクト自身のフィールドをドロップする必要があるからです。`weak` 参照は割り当てを生かしますがオブジェクトは生かさず、`rc` がゼロになると `upgrade()` は失敗します。

すべて `static inline` なので、C コンパイラはプログラム全体を一度に見て、使われないランタイム関数のコストはゼロです。

### 7. ドライバと C コンパイラ（`self/nx.nx`）

`nx build` は C ファイルを `nx-out/` に書き、ビルドモード（`debug`、`safe`、`fast`、`small`）、ターゲットトリプル、`artifact link` の入力に応じたフラグで `zig cc` を起動し、`--keep-c` がなければ C を削除します。同じ経路が `run`、`test`（生成されたテストランナーがエントリポイント）、`leaks`（`-DNX_LEAK_CHECK` を追加）、`size`（`-ffunction-sections` を追加してオブジェクトを読み戻す）にも使われます。

大きなプログラム（ソース約 200 KB。どのプログラムでも `NX_UNITS` で決められます）のデバッグビルドは、代わりに分割されます（決定 116）。`cgen.generate_units` はモジュールごとに一つの C ファイルを `nx-out/<name>.units/` に書き、各オブジェクトにはその C とコマンドラインのハッシュで名前を付けます。ドライバはオブジェクトがないファイルだけを複数のスレッドでコンパイルし、それからリンクします。ランタイムの状態（`NX_STATE`）はルートモジュールのファイルが定義し、他のファイルは宣言します。

`zig cc` が既定なのは、そのままでクロスコンパイルできるからです。Windows マシンからの `--target aarch64-linux-gnu` がそのまま動きます。クロスコンパイルが不要なら `--cc clang` や `--cc gcc` も受け付けます。

### 8. 出荷（`self/ship.nx`、`ship_node.nx`、`installer.nx`。`cgen.nx` の `export_wrapper`）

`nx ship` は `artifact` 宣言を読み、次のものを作ります。

- **`cabi`**：共有ライブラリ、静的アーカイブ、C ヘッダ。
- **`python`**：ctypes ベースのパッケージと wheel。
- **`rustlib`**：アーカイブをリンクするビルドスクリプト、`extern "C"` 宣言、`#[repr(C)]` 構造体、安全なラッパーを持つ Cargo crate。
- **`node`**：共有ライブラリの上に作られた npm パッケージ。
- **`cli`**：実行ファイル。**`installer`**：Inno Setup スクリプト、またはプログラムのファイルを含むインストールスクリプト。

エクスポート境界は、エフェクトが報われる場所です。`!panics` と証明され、エラー共用体を返さないエクスポート関数は、自然な C のシグネチャを得ます。それ以外のエクスポートは `int32_t` のステータスを返し、値を出力引数で渡します。ラッパーはパニック境界を設置するので、ライブラリ内の Nexium のパニックは、アボートではなくホスト側のエラーコードになります。埋め込み可能なアーティファクトを宣言するプログラムでは可変グローバルが拒否されるので、同じライブラリを読み込む二つのホストが互いに干渉することはありません。

## ツール

どれも同じ型付き IR の上のビューなので、コンパイラと食い違いません。

| ツール | 読むもの |
| --- | --- |
| `nx effects` | 伝播後の各インスタンスの `effects` |
| `nx refcounts` | すべての `Retain`/`Release`/`Weak`/`Upgrade` ノードとその関数 |
| `nx audit` | `unsafe` ブロックとグローバル |
| `nx doc` | ドキュメントコメント、シグネチャ、エフェクトを HTML に描画 |
| `nx lsp` | 編集のたびに行う完全な検査からの診断。検査済みインスタンスからのコードレンズ（記録された証人によるパニックの証明）。プログラムの検査が通るときは、定義への移動、名前の変更、ホバーは検査器が各名前を何に解決したか（`self/lsp_index.nx`：ローカル、関数とメソッド、フィールド）から得て、名前の変更はプログラムのすべてのファイルを編集する。そうでないとき、および補完、型、定数は、トークン列と構文解析済みのモジュール（`self/lsp.nx`）から得るので、コードにエラーがあっても応答する |
| `nx repl` | インタプリタを一行ずつ、毎回全体を検査し直すプログラムの上で動かす |
| `nx size` | オブジェクトファイルのセクションサイズを宣言に対応付ける |
| `nx layout` | 検査器の `size_of`/`align_of` をフィールドごとにたどる：オフセット、パディング、合計、そして struct を小さくするアラインメント順の並べ替え |
| `nx fmt` | トークン列だけ。行を結合も分割もしない |

## セルフホスティング

コンパイラは `self/` の下に Nexium で、段階ごとに一ファイルで書かれ、自分自身をビルドします。`bootstrap/nx.c` はコンパイラが自分自身のために出力する C で、どの C コンパイラでもそれを `nx0` にでき、`nx0` は `self/nx.nx` を `nx1` にビルドし、`nx1` は同じ C をもう一度出力しなければなりません（`nx2`）。これがテスト対象のコンパイラであり、リリースが出荷するものです（`bootstrap/build.sh`、`bootstrap/README.md`）。構文木と型付き IR は id アリーナ、すなわち `List` に入ったノードがインデックスで互いを参照する形で（`examples/tree.nx` 参照）、再帰型を必要とせず、一度の解放で済みます。移植の間、各段階はツリー内のすべてのソースについて出力を最初のコンパイラと比較して検証されました。現在スイートを動かすテストハーネスも、それ自体が Nexium プログラムの `tests/run.nx` です。

## 何かがおかしいときに見る場所

| 症状 | ここから |
| --- | --- |
| 構文解析が通るべきでないのに通る、またはその逆 | `self/parser.nx`、次に期待されるメッセージがある `tests/compile_fail/` |
| おかしく見える型エラー | `self/check_exprs.nx` の `check_expr`、`self/check_calls.nx` の `check_method_call` |
| あるべきエフェクトがない、またはあるべきでないエフェクトがある | `own_effects` の証人。`self/check*.nx` で `add_effect` を grep |
| `nx leaks` でのリーク | `self/cgen.nx` のスコープスタック（`register_drop`）。所有された一時値はすべて登録が必要 |
| 生成された C がコンパイルできない | `nx emit-c file.nx --keep-c` で `nx-out/file.c` を読む（`emit-c` は `#line` を書かないので、C コンパイラは C の行を指す）。呼んでいるランタイムのヘルパは `runtime/nx_rt.h` にある |
| `for parallel` や `using arena` の中でのクラッシュ | `self/cgen.nx` の `parallel_for` と、ランタイムのアリーナの節 |
